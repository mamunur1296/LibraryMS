# Top 25+ Scenario-Based Interview Q&A (For 3 YOE Backend Engineer)

৩ বছরের অভিজ্ঞতাসম্পন্ন একজন ব্যাকএন্ড বা ডেটাবেস ইঞ্জিনিয়ারের জন্য ইন্টারভিউতে সাধারণত "রিয়েল-লাইফ সিনারিও" বা "প্রবলেম সলভিং" রিলেটেড প্রশ্ন বেশি করা হয়। এখানে আপনার শেখা কনসেপ্টগুলোর ওপর ভিত্তি করে সবচেয়ে গুরুত্বপূর্ণ ২৬টি রিয়েল-টাইম ইন্টারভিউ প্রশ্ন ও তার উত্তর সাজানো হলো।

## 🚀 পার্ট ১: আর্কিটেকচার এবং পারফরম্যান্স অপ্টিমাইজেশন (Architecture & Optimization)

### ১. Query Optimization Troubleshooting
**প্রশ্ন:** "আমাদের একটি API থেকে ডেটা লোড হতে ৫ সেকেন্ড সময় লাগছে। আপনি ব্যাকএন্ড ডেভেলপার হিসেবে কীভাবে এই SQL কুয়েরিটি ট্রাবলশুট এবং ফাস্ট করবেন?"
**উত্তর:** "প্রথমেই আমি SSMS-এ কুয়েরিটি চালিয়ে এর **Execution Plan** চেক করব। আমি দেখব সেখানে কোনো **Table Scan** বা **Index Scan** হচ্ছে কি না। যদি হয়, তবে উপযুক্ত কলামে **Non-Clustered Index** তৈরি করে সেটিকে **Index Seek**-এ কনভার্ট করব। এরপর দেখব অপ্রয়োজনীয় `SELECT *` ব্যবহার করা হয়েছে কি না; শুধু দরকারি কলামগুলো সিলেক্ট করে Covering Index তৈরি করব। অনেক সময় Statistics আউটডেটেড থাকার কারণে ইনডেক্স কাজ করে না, তাই স্ট্যাটিস্টিকস আপডেট করব।"

### ২. Normalization বনাম Denormalization
**প্রশ্ন:** "নরমালাইজেশন ডেটার ডুপ্লিকেশন কমায়, এটা আমরা জানি। কিন্তু এমন কোনো সিচুয়েশন কি আছে যেখানে আপনি ইচ্ছে করে নরমালাইজেশন ব্রেক করে Denormalization করবেন?"
**উত্তর:** "হ্যাঁ, Read-Heavy অ্যাপ্লিকেশনের ক্ষেত্রে। নরমালাইজেশনের কারণে ডেটা অনেকগুলো টেবিলে ভাগ হয়ে যায়, ফলে রিড করার সময় অনেক `JOIN` করতে হয় যা বড় টেবিলে স্লো। পারফরম্যান্স বাড়ানোর জন্য আমরা Denormalization করি। যেমন: 'অর্ডার' টেবিলের সাথে বারবার 'অর্ডার ডিটেইলস' জয়েন করে Total Price বের করার বদলে, আমরা সরাসরি 'অর্ডার' টেবিলেই একটি `TotalAmount` কলাম রাখতে পারি।"

### ৩. Partitioning (বিশাল টেবিল ম্যানেজমেন্ট)
**প্রশ্ন:** "আমাদের 'Logs' টেবিলে গত ৫ বছরে ৫০ মিলিয়ন ডেটা জমেছে। এখন সার্চ বা ইনসার্ট অনেক স্লো। আপনি এর সমাধান কী করবেন?"
**উত্তর:** "আমি **Table Partitioning** ব্যবহার করব। ডেটাকে সাল (Year) বা মাস অনুযায়ী লজিক্যালি আলাদা পার্টিশনে ভাগ করব। এর সুবিধা হলো, ইউজার যখন চলতি মাসের ডেটা খুঁজবে, তখন ডেটাবেস ৫০ মিলিয়ন ডেটা না খুঁজে শুধু চলতি মাসের পার্টিশনে (Partition Elimination) খুঁজবে। আর পুরোনো ডেটাগুলো আমরা সস্তা স্টোরেজে আর্কাইভ করে রাখতে পারব।"

### ৪. Joins-এর পারফরম্যান্স
**প্রশ্ন:** "INNER JOIN এবং LEFT JOIN এর মধ্যে পারফরম্যান্সে কী কোনো পার্থক্য আছে? কখন কোনটি ব্যবহার করবেন?"
**উত্তর:** "**INNER JOIN** তুলনামূলকভাবে ফাস্ট, কারণ এটি শুধু ম্যাচ করা ডেটাগুলোকেই ফিল্টার করে আনে। অন্যদিকে, **LEFT JOIN** বাম দিকের টেবিলের সব ডেটা রেখে দেয় এবং ম্যাচ না পেলেও মেমোরিতে প্রসেস করে Null বসায়। তাই যেখানে নিশ্চিতভাবে শুধু ম্যাচিং ডেটাই লাগবে, সেখানে আমি সবসময় INNER JOIN ব্যবহার করব।"

### ৫. UNION বনাম UNION ALL
**প্রশ্ন:** "দুটি ভিন্ন টেবিল থেকে আমাদের ১ মিলিয়ন করে মোট ২ মিলিয়ন রেকর্ড একসাথে দেখাতে হবে। আপনি কি UNION ব্যবহার করবেন নাকি UNION ALL? কেন?"
**উত্তর:** "আমি অবশ্যই **UNION ALL** ব্যবহার করব (যদি ডুপ্লিকেট ডেটা নিয়ে আমার সমস্যা না থাকে)। কারণ `UNION` ডেটাগুলোকে এক করার পর ডুপ্লিকেট রিমুভ করার জন্য ইন্টারনালি একটি 'Sort' অপারেশন চালায়, যা ২ মিলিয়ন রেকর্ডের জন্য খুবই এক্সপেনসিভ এবং স্লো। `UNION ALL` কোনো সর্টিং করে না, সরাসরি ডেটা যোগ করে দেয়, তাই এটি অনেক ফাস্ট।"

### ৬. Clustered বনাম Non-Clustered Index
**প্রশ্ন:** "একটি টেবিলে মাত্র একটি Clustered Index থাকতে পারে। একটি Users টেবিলে আপনি কোন কলামটিকে Clustered Index এর জন্য বেছে নেবেন এবং কেন?"
**উত্তর:** "আমি Primary Key (যেমন: `UserId` যা একটি Auto-incremented Integer) কলামকে Clustered Index হিসেবে বেছে নেব। কারণ Clustered Index ফিজিক্যালি ডেটাকে সর্ট করে রাখে। Integer ভ্যালু সবসময় বাড়ে (Sequential), তাই নতুন ডেটা ইনসার্ট হলে তা টেবিলের শেষে অ্যাড হবে (Page Split হবে না)। GUID বা Random String-এর ওপর Clustered Index বানালে প্রচুর Fragmentation হবে।"

## 🔒 পার্ট ২: কনকারেন্সি, লকিং এবং ট্রানজেকশন (Concurrency & Transactions)

### ৭. Concurrency Handling
**প্রশ্ন:** "লাইব্রেরি সিস্টেমে একটি বইয়ের মাত্র ১টি কপি স্টকে আছে। ২ জন ইউজার ঠিক একই মিলি-সেকেন্ডে বইটি ইস্যু করার রিকোয়েস্ট দিল। কীভাবে হ্যান্ডেল করবেন যেন স্টক মাইনাস (-) না হয়ে যায়?"
**উত্তর:** "আমি **Optimistic Concurrency** ব্যবহার করব। টেবিলে একটি `RowVersion` কলাম রাখব। আপডেট করার সময় চেক করব ডেটা রিড করার পর অন্য কেউ চেঞ্জ করেছে কি না। করলে ২য় ইউজারকে Concurrency Exception থ্রো করব। ওয়েব অ্যাপ্লিকেশনের জন্য এটি বেস্ট, কারণ এতে ডেটাবেস লক (Pessimistic Locking) হয়ে বসে থাকে না।"

### ৮. Deadlock Resolution
**প্রশ্ন:** "প্রোডাকশন ডেটাবেসে দুটি Stored Procedure বারবার Deadlock তৈরি করছে। আপনি কীভাবে এটি ট্রাবলশুট এবং ফিক্স করবেন?"
**উত্তর:** "প্রথমে আমি SQL Server-এর Extended Events বা SQL Profiler ব্যবহার করে ডেডলক গ্রাফ (Deadlock Graph) কালেক্ট করব। এটি আমাকে বলে দেবে কোন টেবিল বা ইনডেক্সে লক হচ্ছে। ফিক্স করার জন্য আমি নিশ্চিত করব যে দুটি SP যেন একই সিরিয়ালে (Same Order) টেবিলগুলো অ্যাক্সেস করে। এছাড়াও, ছোট এবং ফাস্ট ট্রানজেকশন লেখা এবং উপযুক্ত ইনডেক্স ব্যবহার করা ডেডলক কমাতে সাহায্য করে।"

### ৯. Transaction Isolation Levels
**প্রশ্ন:** "দিন শেষে ফিন্যান্সিয়াল রিপোর্ট জেনারেট হতে ১০ মিনিট লাগে। এই সময় অন্য ইউজাররা ডেটা ইনসার্ট করতে গেলে ব্লক হয়ে যাচ্ছে (লক)। রিপোর্টও সঠিক ডেটা নিয়ে জেনারেট হতে হবে। সমাধান কী?"
**উত্তর:** "আমি রিপোর্টের কুয়েরিটির জন্য **Snapshot Isolation Level** বা `READ COMMITTED SNAPSHOT` ব্যবহার করব। এটি ডেটাবেসে লকের বদলে `tempdb`-তে ডেটার একটি ভার্সন (Row Versioning) তৈরি করে রাখে। ফলে রিপোর্ট জেনারেট করার সময় ডেটা রিড করতে কাউকে ব্লক করবে না, আবার রিপোর্টটিও একটি কনসিস্টেন্ট ডেটা পাবে।"

### ১০. Foreign Key Impacts (Cascade vs Restrict)
**প্রশ্ন:** "ইউজার টেবিলের সাথে অর্ডার টেবিলের রিলেশন আছে। আপনি `ON DELETE CASCADE` সেট করলেন। প্রোডাকশনে এর রিস্ক কী?"
**উত্তর:** "রিস্ক হলো, যদি ভুলবশত বা কোনো বাগের কারণে একজন ইম্পরট্যান্ট ইউজারের ডেটা ডিলিট হয়ে যায়, তবে তার করা বিগত ৫ বছরের সমস্ত অর্ডার, পেমেন্ট হিস্ট্রি স্বয়ংক্রিয়ভাবে মুছে যাবে (Cascade)। এন্টারপ্রাইজ অ্যাপ্লিকেশনে সাধারণত CASCADE এড়িয়ে চলা হয় এবং এর বদলে **Soft Delete** (IsDeleted = true) ব্যবহার করা হয়।"

## 💻 পার্ট ৩: T-SQL এবং প্রোগ্রামেবিলিটি (T-SQL & Programmability)

### ১১. Stored Procedure বনাম UDF (Function)
**প্রশ্ন:** "আমাদের একটি SELECT কুয়েরির ভেতরে প্রতিটি অর্ডারের ট্যাক্স (Tax) হিসাব করতে হবে। আপনি কি লজিকটি Stored Procedure-এ লিখবেন নাকি Function-এ? কেন?"
**উত্তর:** "আমি **User Defined Function (UDF)** (বিশেষ করে Scalar Function) ব্যবহার করব। কারণ Function-কে সরাসরি `SELECT` স্টেটমেন্টের ভেতরে কল করা যায় (যেমন: `SELECT OrderId, dbo.CalculateTax(Amount) FROM Orders`), কিন্তু Stored Procedure-কে `SELECT` স্টেটমেন্টের ভেতরে কল করা যায় না, اسے `EXEC` দিয়ে কল করতে হয়।"

### ১২. Temporary Tables বনাম Table Variables
**প্রশ্ন:** "একটি SP-এর ভেতর আপনাকে ১ লক্ষ ডেটা সাময়িকভাবে প্রসেস করতে হবে। আপনি কি Temp Table (`#Table`) ব্যবহার করবেন নাকি Table Variable (`@Table`)?"
**উত্তর:** "আমি **Temp Table (`#Table`)** ব্যবহার করব। Table Variable ছোট ডেটার (সাধারণত ১০০-১০০০ রো) জন্য ভালো, কিন্তু এটি কোনো Statistics মেইনটেইন করে না, ফলে ১ লক্ষ ডেটার ক্ষেত্রে Execution Plan খুবই বাজে হবে। Temp Table-এ ইনডেক্স বসানো যায় এবং এটি Statistics মেইনটেইন করে, তাই বড় ডেটার জন্য এটি ফাস্ট।"

### ১৩. Triggers (Anti-pattern)
**প্রশ্ন:** "আপনার টিম লিড আপনাকে বলল, অর্ডার ইনসার্ট হওয়ার পর ইউজারের ব্যালেন্স কাটার লজিকটি একটি `AFTER INSERT` Trigger-এর ভেতর লিখতে। এটি কেন একটি ব্যাড প্র্যাকটিস হতে পারে?"
**উত্তর:** "Trigger হলো Hidden Magic। ডেভেলপাররা অ্যাপ্লিকেশন কোড দেখে বুঝতে পারে না যে ব্যাকগ্রাউন্ডে ব্যালেন্স কাটা যাচ্ছে। এতে ডিবাগ করা খুব কঠিন হয়। এছাড়া, Trigger একই ট্রানজেকশনের অংশ হওয়ায়, ব্যালেন্স কাটার লজিকে কোনো সমস্যা হলে মূল ইনসার্ট অপারেশনও ফেইল করবে। এই লজিকটি API লেভেলে (Service Layer) বা একটি Stored Procedure-এ লেখা উচিত।"

### ১৪. HAVING বনাম WHERE
**প্রশ্ন:** "আপনি চান ২০২৩ সালের অর্ডারগুলো ফিল্টার করতে, এবং তারপর যেসব ইউজারের ৫টির বেশি অর্ডার আছে তাদের বের করতে। কোনটি WHERE-এ যাবে আর কোনটি HAVING-এ?"
**উত্তর:** "২০২৩ সালের ফিল্টারটি **WHERE** ক্লজে যাবে (যেমন: `WHERE OrderYear = 2023`), কারণ এটি গ্রুপ করার আগেই ফিল্টার করে ডেটাসেট ছোট করে ফেলবে। আর ৫টির বেশি অর্ডারের শর্তটি **HAVING** ক্লজে যাবে (যেমন: `HAVING COUNT(OrderId) > 5`), কারণ এটি GROUP BY হওয়ার পর এগ্রিগেটেড ডেটার ওপর কন্ডিশন চেক করবে।"

### ১৫. Pagination in SQL
**প্রশ্ন:** "১ মিলিয়ন ইউজারের টেবিল থেকে আপনি পেজ ৫ এর ডেটা (প্রতি পেজে ৫০ জন) কীভাবে সবচেয়ে ইফিশিয়েন্ট উপায়ে আনবেন?"
**উত্তর:** "আমি SQL Server-এর `OFFSET ... FETCH` ব্যবহার করব। 
কুয়েরিটি হবে: `ORDER BY UserId OFFSET 200 ROWS FETCH NEXT 50 ROWS ONLY;` (যেখানে 200 হলো (5-1) * 50)। এটি পুরোনো `ROW_NUMBER()` দিয়ে পেজিনেশন করার চেয়ে অনেক বেশি স্ট্যান্ডার্ড এবং রিডেবল।"

### ১৬. SQL Injection
**প্রশ্ন:** "SQL Injection কীভাবে ঘটে এবং .NET (EF Core / ADO.NET) কীভাবে এটি প্রতিহত করে?"
**উত্তর:** "যখন ইউজারের ইনপুট সরাসরি স্ট্রিং কনক্যাটেনেশন (`"SELECT * FROM Users WHERE Name = '" + name + "'"`) করে কুয়েরি চালানো হয়, তখন ইউজার ক্ষতিকর SQL ইনজেক্ট করতে পারে (যেমন: `'; DROP TABLE Users; --`)। .NET-এ **Parameterization** (যেমন: `@Name` প্যারামিটার পাঠানো) ব্যবহার করা হয়। ডেটাবেস প্যারামিটারকে কোড হিসেবে না ধরে শুধু 'ভ্যালু' হিসেবে ট্রিট করে, তাই ইনজেকশন কাজ করে না।"

## ⚙️ পার্ট ৪: ORM (.NET EF Core / LINQ)

### ১৭. LINQ N+1 Query Problem
**প্রশ্ন:** "প্রোফাইলার চেক করে দেখলেন ব্যাকএন্ড থেকে ১টি রিকোয়েস্টের জন্য ডেটাবেসে ১০০টি কুয়েরি ফায়ার হয়েছে। এটি কেন হয় এবং সমাধান কী?"
**উত্তর:** "এটি **N+1 Query Problem**। Lazy Loading-এর কারণে লুপের ভেতর চাইল্ড এন্টিটি কল করলে প্রতি লুপে একটি করে কুয়েরি ফায়ার হয়। সমাধান হলো Eager Loading ব্যবহার করা। LINQ-এ `.Include()` ব্যবহার করলে EF Core একটি মাত্র `JOIN` কুয়েরি তৈরি করে সব ডেটা একসাথে ফেচ করে আনবে।"

### ১৮. IQueryable বনাম IEnumerable
**প্রশ্ন:** "আপনি একটি ডেটাসেটের ওপর `.ToList()` কল করার পর `.Where(x => x.Age > 20)` কল করলেন (IEnumerable)। এর ইমপ্যাক্ট কী?"
**উত্তর:** "এর ইমপ্যাক্ট খুবই মারাত্মক। `.ToList()` কল করার সাথে সাথেই ডেটাবেস থেকে **সব** ডেটা র‍্যামে (Client Memory) চলে আসবে। এরপর `.Where()` ফিল্টারটি C# মেমোরিতে কাজ করবে। যদি ডেটাবেসে ১ লক্ষ রেকর্ড থাকে, তবে সব র‍্যামে লোড হবে। এর বদলে `.Where()` আগে দিয়ে শেষে `.ToList()` দিলে (IQueryable), SQL Server নিজেই ফিল্টার করে শুধু প্রয়োজনীয় ডেটা পাঠাত।"

### ১৯. AsNoTracking (EF Core Optimization)
**প্রশ্ন:** "আপনি শুধু ওয়েবসাইটে বইয়ের লিস্ট দেখানোর জন্য (Read-only) ডেটা ফেচ করছেন। EF Core-এ কোন পারফরম্যান্স অপ্টিমাইজেশনটি ব্যবহার করবেন?"
**উত্তর:** "আমি `.AsNoTracking()` ব্যবহার করব। বাই ডিফল্ট EF Core ডেটাবেস থেকে ডেটা আনার পর মেমোরিতে তার চেঞ্জ ট্র্যাক করে (Change Tracker)। যেহেতু আমি ডেটা আপডেট করব না, শুধু রিড করব, তাই ট্র্যাকিং অফ করে দিলে মেমোরি খরচ অনেক কমে যায় এবং কুয়েরি ফাস্ট হয়।"

### ২০. Bulk Inserts in EF Core
**প্রশ্ন:** "আপনাকে একটি এক্সেল ফাইল থেকে ৫০,০০০ ডেটা ডেটাবেসে সেভ করতে হবে। লুপ চালিয়ে `DbContext.Add()` করলে অনেক সময় লাগছে। বিকল্প কী?"
**উত্তর:** "লুপ চালিয়ে অ্যাড করলে প্রতিবার সেভ করার সময় একটি করে `INSERT` কুয়েরি তৈরি হয় যা খুবই স্লো। এর বদলে আমি `SqlBulkCopy` (ADO.NET) অথবা EF Core-এর থার্ড-পার্টি লাইব্রেরি যেমন `EFCore.BulkExtensions` ব্যবহার করব, যা একবারে হাজার হাজার ডেটা ব্যাচ আকারে ইনসার্ট করে দেয়।"

### ২১. Soft Delete বনাম Hard Delete
**প্রশ্ন:** "ডেটা ডিলিট করার সময় আমরা হার্ড ডিলিটের (DELETE FROM) বদলে Soft Delete (`IsDeleted = true`) কেন বেশি ব্যবহার করি?"
**উত্তর:** "হার্ড ডিলিট করলে ডেটা চিরতরে হারিয়ে যায়, যা অডিট বা হিস্ট্রির জন্য খারাপ। এছাড়াও হার্ড ডিলিট ফিজিক্যাল ইনডেক্সে ফ্র্যাগমেন্টেশন তৈরি করে। সফট ডিলিট মূলত একটি `UPDATE` অপারেশন, যা ডেটা হিস্ট্রি ধরে রাখে। তবে সফট ডিলিটের ক্ষেত্রে সব `SELECT` কুয়েরিতে `IsDeleted = 0` ফিল্টারটি মাথায় রাখতে হয় (EF Core Global Query Filter দিয়ে এটি সহজে মেইনটেইন করা যায়)।"

### ২২. Caching Strategy (Redis)
**প্রশ্ন:** "একটি ইভেন্ট ম্যানেজমেন্ট সাইটে একটি নির্দিষ্ট ইভেন্টের পেজে হুট করে প্রচুর ট্রাফিক এলো। ডেটাবেসের CPU Usage ৯০% হয়ে গেছে। ডেটাবেস ক্র্যাশ থেকে বাঁচাতে কী করবেন?"
**উত্তর:** "আমি **Cache-Aside Pattern** ব্যবহার করে Redis বা In-memory Cache ইমপ্লিমেন্ট করব। ইউজার প্রথমবার রিকোয়েস্ট দিলে ডেটাবেস থেকে ডেটা এনে ক্যাশে রেখে দেব (ধরা যাক ৫ মিনিটের জন্য)। পরবর্তী সব ইউজার ওই ৫ মিনিট ডেটাবেসের বদলে ক্যাশ থেকে ডেটা পাবে। এতে ডেটাবেসের লোড এক ধাক্কায় প্রায় জিরোতে নেমে আসবে।"

### ২৩. Sharding বনাম Partitioning
**প্রশ্ন:** "আপনার ডেটাবেসের সাইজ ২ টেরাবাইট ছাড়িয়ে গেছে। আপনি কি Partitioning করবেন নাকি Sharding? পার্থক্য কী?"
**উত্তর:** "আমি প্রথমে **Partitioning** করার চেষ্টা করব। পার্টিশনিং একই ডেটাবেস সার্ভারের ভেতরে ডেটাকে লজিক্যালি ভাগ করে, তাই অ্যাপ্লিকেশন কোড খুব একটা পরিবর্তন করতে হয় না। 
তবে যদি ট্রাফিক এতো বেশি হয় যে ১টি সার্ভারের প্রসেসর আর কুলাতে পারছে না, তখন আমি **Sharding** করব। শার্ডিং ডেটাকে ফিজিক্যালি আলাদা সার্ভারে ভাগ করে (যেমন: এশিয়ার ডেটা সার্ভার-১ এ, ইউরোপের ডেটা সার্ভার-২ এ)। শার্ডিং অনেক কমপ্লেক্স এবং কোডে প্রচুর পরিবর্তন করতে হয়।"

### ২৪. Database Migrations in CI/CD
**প্রশ্ন:** "আপনার লোকাল মেশিনে EF Core Migration তৈরি করেছেন। প্রোডাকশন ডেটাবেসে এই মাইগ্রেশন কীভাবে রান করা সবচেয়ে সেইফ?"
**উত্তর:** "প্রোডাকশনে কখনোই অ্যাপ্লিকেশন স্টার্টআপের সময় `context.Database.Migrate()` রান করা উচিত নয় (এতে কনকারেন্সি ইস্যু বা ডেটা লস হতে পারে)। বেস্ট প্র্যাকটিস হলো CI/CD পাইপলাইনে `dotnet ef migrations script` কমান্ড ব্যবহার করে SQL স্ক্রিপ্ট জেনারেট করা। এরপর ওই SQL স্ক্রিপ্টটি DBA বা ডেপ্লয়মেন্ট টুল (যেমন: Flyway, DbUp বা Azure DevOps) দিয়ে প্রোডাকশনে চালানো।"

### ২৫. CAP Theorem in Banking System
**প্রশ্ন:** "CAP Theorem অনুযায়ী Consistency, Availability, Partition Tolerance-এর মধ্যে একটি ব্যাংকিং সিস্টেমে আপনি কোনটিকে সবচেয়ে বেশি প্রায়োরিটি দেবেন এবং কেন?"
**উত্তর:** "ব্যাংকিং সিস্টেমে আমি **Consistency (C)** এবং **Partition Tolerance (P)** (অর্থাৎ CP সিস্টেম) কে প্রায়োরিটি দেব। ব্যালেন্স আপডেটের ক্ষেত্রে ডেটা সবসময় সঠিক (Consistent) হতে হবে। নেটওয়ার্ক পার্টিশন হলে সিস্টেম হয়তো সাময়িকভাবে স্লো বা আন-অ্যাভেইলেবল (Availability স্যাক্রিফাইস) হবে, কিন্তু কোনোভাবেই ভুল ব্যালেন্স দেখানো বা ট্রানজেকশন হারানো যাবে না।"

### ২৬. Read/Write Splitting (CQRS Pattern)
**প্রশ্ন:** "অ্যাপ্লিকেশনে রিড অপারেশন অনেক বেশি। ডেটাবেসে ইনসার্ট বা আপডেট করতে গেলে লক হয়ে যাচ্ছে। স্কেলিংয়ের জন্য আর্কিটেকচার লেভেলে কী পরিবর্তন আনবেন?"
**উত্তর:** "আমি **Read/Write Splitting** বা **CQRS (Command Query Responsibility Segregation)** প্যাটার্ন ইমপ্লিমেন্ট করব। অর্থাৎ ইনসার্ট/আপডেট (Write) করার জন্য একটি প্রাইমারি (Master) ডেটাবেস থাকবে। আর ডেটা দেখানোর (Read) জন্য একাধিক রেপ্লিকা (Slave) ডেটাবেস থাকবে। প্রাইমারি ডেটাবেস থেকে ব্যাকগ্রাউন্ডে ডেটা রেপ্লিকাতে সিংক হবে। এতে রিড এবং রাইট একে অপরকে ব্লক করবে না।"

## 🎯 ভবিষ্যৎ শিক্ষার টার্গেট (Next Learning Roadmap)
এখানে এমন কিছু সিস্টেম ডিজাইন এবং অ্যাডভান্সড কনসেপ্ট দেওয়া হলো, যেগুলো আপনি এখনও শেখেননি কিন্তু একজন মিড-লেভেল বা সিনিয়র ব্যাকএন্ড ইঞ্জিনিয়ার হিসেবে আপনার জানা উচিত:

### ১. T-SQL-এর অ্যাডভান্সড কুয়েরি (খুবই গুরুত্বপূর্ণ)
ইন্টারভিউতে সবচেয়ে বেশি কোডিং টেস্ট বা প্রবলেম সলভিং দেওয়া হয় এই টপিকগুলো থেকে:
* **Window Functions:** `ROW_NUMBER()`, `LEAD()`, `LAG()`, `RANK()` (যেমন: "প্রত্যেক ডিপার্টমেন্টের সর্বোচ্চ স্যালারি পাওয়া এমপ্লয়িকে বের করো")।
* **CTEs (Common Table Expressions):** সাবকুয়েরিকে সুন্দর করে লেখার জন্য `WITH` ক্লজের ব্যবহার।
* **Recursive CTE:** এমপ্লয়ি-ম্যানেজার হায়ারার্কি বা ট্রি-স্ট্রাকচার (Tree Structure) ডেটা বের করার জন্য।
* **CROSS APPLY / OUTER APPLY:** মূলত ফাংশনের রেজাল্টের সাথে টেবিল জয়েন করার জন্য।

### ২. .NET Entity Framework (EF Core) অ্যাডভান্সড
EF Core-এর কিছু হিডেন ফিচার যা সিনিয়র রোলে কাজ করতে লাগে:
* **Global Query Filters:** সব কুয়েরিতে বারবার `Where(x => !x.IsDeleted)` না লিখে গ্লোবালি কীভাবে Soft Delete হ্যান্ডেল করবেন।
* **EF Core Interceptors:** ডেটা সেভ হওয়ার ঠিক আগে স্বয়ংক্রিয়ভাবে `CreatedAt` বা `ModifiedBy` বসিয়ে দেওয়ার ম্যাজিক।
* **Compiled Queries:** এমন কোনো কুয়েরি যা অ্যাপ্লিকেশনে হাজারবার কল হয়, তাকে কীভাবে Compiled Query বানিয়ে সুপারফাস্ট করা যায়।
* **Concurrency Token (`[Timestamp]`):** কোডের মাধ্যমে প্র্যাকটিক্যালি Optimistic Concurrency কীভাবে ইমপ্লিমেন্ট করবেন।

### ৩. মাইক্রোসার্ভিস ও ডিস্ট্রিবিউটেড ডেটাবেস আর্কিটেকচার
৩ বছরের এক্সপেরিয়েন্সে আপনার সিস্টেম ডিজাইনের নলেজ চেক করা হবে:
* **Saga Pattern:** ধরুন, ই-কমার্সে পেমেন্ট সাকসেস হয়েছে কিন্তু ইনভেন্টরি আপডেট ফেইল করেছে। তখন অন্য ডেটাবেসের পেমেন্ট কীভাবে রোলব্যাক করবেন (Distributed Transaction)?
* **Database per Service বনাম Shared Database:** মাইক্রোসার্ভিস আর্কিটেকচারে কখন আলাদা ডেটাবেস নেওয়া উচিত আর কখন উচিত নয়।
* **Event Sourcing:** শুধু কারেন্ট ব্যালেন্স সেভ না করে, ব্যালেন্সের সমস্ত পরিবর্তন (Events) ডেটাবেসে লগ করে রাখা।

### ৪. মডার্ন SQL Server ফিচার
* **Change Data Capture (CDC):** ডেটাবেসের কোনো টেবিলে ডেটা ইনসার্ট/আপডেট/ডিলিট হলে তার ট্র্যাক বা হিস্ট্রি ট্রিগার ছাড়াই কীভাবে রাখা যায়।
* **Temporal Tables:** সিস্টেম ভার্সন টেবিল, যা অটোমেটিকভাবে হিস্ট্রি রাখে এবং "গত মাসের ১ তারিখে ডেটার অবস্থা কী ছিল" তা বের করতে পারে।

### ৫. NoSQL এবং অন্যান্য ডেটাবেসের ব্যবহার
সব জায়গায় SQL Server বা Relational DB ব্যবহার করা ঠিক নয়। ইন্টারভিউতে জানতে চাইতে পারে:
* কখন **SQL Server** ব্যবহার করবেন?
* কখন **MongoDB** (Document Database) ব্যবহার করবেন?
* কখন **Redis** (Key-Value/Cache) ব্যবহার করবেন? 
* কখন **ElasticSearch** (টেক্সট সার্চিংয়ের জন্য) ব্যবহার করবেন?
