⚠️ Known Gap — Admin vs Borrow Actions:
The BorrowsController uses [Authorize(Roles = "Librarian")] on POST /api/borrows, /api/borrows/return, and /api/borrows/{id}/pay-fine. The Admin role is not listed, so an Admin user receives 403 Forbidden trying to issue/return/pay fines through the API. The frontend shows the buttons to Admin, but they will fail on the server.
⚠️ Security Gap — Registration Allows Any Role:
POST /api/auth/register accepts role: "Admin" with no server-side guard. Anyone can register as Admin and gain full system control. Fix: restrict registration to Member only, or allow Member/Librarian at most.

Steps:
1. Member places reservation on a book with 0 available copies
2. Reservation is Pending at queue position N
3. Librarian returns a copy → system sets reservation to Available with expiry = now + 24h
4. Member sees status change on GET /api/reservations/my-reservations
5. Librarian issues the book to the member → reservation → Fulfilled
6. If not fulfilled within 24h → reservation → Expired; next in queue notified

6. End-to-End Business Flows

6.1 Borrow → Overdue → Return → Pay Fine (Full Cycle)

Phase 1: Librarian issues book
  POST /api/borrows → 201
  Assert: Status=Active, DueDate=+14d, LateFine=0

Phase 2: Member views active borrows (day 1)
  GET /api/borrows/my-active → borrow appears
  Assert: books availability count decremented

Phase 3: Book becomes overdue (after day 14)
  Hangfire OverdueCheckJob runs (daily 02:00 UTC)
  OR Manual call → system updates Status=Overdue
  GET /api/reports/overdue?fromDate=... → borrow appears
  Assert: OverdueDays > 0, LateFine = OverdueDays × $2

Phase 4: Librarian returns book
  POST /api/borrows/return { borrowId } → 200
  Assert: Status=Returned, ReturnDate set, LateFine computed
  Assert: books availability count incremented

Phase 5: Librarian processes fine payment
  POST /api/borrows/{id}/pay-fine → 200
  Assert: IsFinePaid=true

Phase 6: Verify dashboard reflects changes
  GET /api/reports/dashboard
  Assert: ActiveBorrows decreased, TotalLateFinesCollected increased,
          PendingLateFines decreased

6.2 Reserve → Notify → Fulfill (Full Cycle)

Phase 1: Member places reservation (all copies borrowed out)
  POST /api/reservations → 201
  Assert: Status=Pending, QueuePosition=1

Phase 2: Librarian returns a copy
  POST /api/borrows/return → triggers domain event
  → Reservation notified: Status=Available, ExpiresAt=now+24h

Phase 3: Member sees reservation is available
  GET /api/reservations/my-reservations
  Assert: Status=Available

Phase 4: Librarian issues the book to the reserving member
  POST /api/borrows { memberId, bookCopyId, ... } → 201
  → Reservation: Status=Fulfilled

Phase 5: Reservation auto-expires if unfulfilled
  Wait 24h → Hangfire ReservationExpiryJob runs
  Assert: Status=Expired
  Next queue position gets notified

6.3 Member Enrollment + Account Creation

Phase 1: Admin/Librarian creates member record
  POST /api/members { firstName, lastName, email, phone, username, password } → 201
  Assert: MemberDto returned with MembershipNumber="LIB-{year}-{sequential}"

Phase 2: Member logs in with created credentials
  POST /api/auth/login { username, password } → JWT

Phase 3: Member updates profile
  POST /api/users/change-email { newEmail } → 200
  POST /api/users/change-password { currentPassword, newPassword } → 200
  Next login requires new password

Phase 4: Member is suspended (by Admin/Librarian)
  POST /api/members/{id}/suspend { suspendedUntil, reason } → 200
  Assert: Member.Status=Suspended
  POST /api/borrows → by Librarian for this member → DomainException thrown
  Assert: 400 Domain error "Member is suspended"

Phase 5: Suspension expires or Admin activates
  POST /api/members/{id}/activate → 200
  Assert: Member.Status=Active
  Borrow works again
